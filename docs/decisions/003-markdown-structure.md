# 003: Markdown structure for agent consumption

Status: accepted for the spike

## Context

The Markdown generated by this repository is meant to be read by agents (an MCP server, a Copilot Studio agent, a coding assistant), not primarily by people. An agent typically has three needs:

1. **Discover** which documents exist and which one is relevant for a question.
2. **Fetch a slice**: a whole component file is 15 KB of text plus 42 images for the Accordion; an agent asking about focus behaviour needs one chapter, not the file.
3. **Connect** the design guidance to the code component (`DSAccordion` in `@stihl-design-system/components`) whose props and examples live in Storybook and are served by the existing MCP server and `llms-full.txt`.

Two candidate shapes for the output existed:

- **Faithful extraction**: the Figma documentation as the designers structured it (boards, sections, images), one file per component.
- **Curated AI guideline**: the 18 section template proposed by Patrick Wiesenhuetter (Metadata, Purpose, Semantic Role, When to Use, When NOT to Use, Anatomy, Variants, States, Content Rules, API / Properties, Composition, Responsive Behavior, Accessibility, Correct Examples, Anti-Patterns, Dependencies, Implementation Notes, Acceptance Criteria), attached to [DS-1524](https://andreasstihl.atlassian.net/browse/DS-1524) together with a hand written `DSAccordion.md` sample. The template is kept in [docs/templates/ai-guidelines-template.md](../templates/ai-guidelines-template.md).

The template cannot be produced by extraction alone. Roughly half of its sections (Purpose, Semantic Role, API / Properties, Composition, Acceptance Criteria, Correct Examples with code) need Storybook props, code knowledge or editorial judgement that is not in Figma. Filling them heuristically from Figma text would put invented structure between the designers and the reader, and every Figma edit would silently reshuffle it.

## Decision

**Two layers. This repository produces the source layer faithfully; the curated layer is composed from it later.**

### Layer 1: extracted design documentation (this repository, generated)

- One file per document at `docs/<category>/<id>.md`, categories `components/`, `patterns/`, `foundations/`. Images in `docs/<category>/<id>/`. The category mirrors the Figma library split (Core Components, Pattern Library, Styles) and the `Category` field of the template.
- `#` is the document title. `##` chapters are the Figma boards, `###` and `####` the sections inside them. The board names (`Formatting and Construction`, `Content and Assets`, `Behavior`, `Examples/Variants`) come from the designers' documentation template and are therefore stable across components without any mapping in code.
- **Heading levels never skip.** Figma boards often go from a board title straight to a section title (H2 to H4). The renderer closes those gaps so an agent can split the file by heading and always gets a well formed tree. Sibling relations are preserved (an H3 following a promoted H4 stays an H3).
- **Frontmatter is the metadata table.** `component`, `title`, `category`, `importName`, `package`, `keywords`, the Figma source (`figmaFileKey`, `figmaNodeId`, `sourceUrl`) and the published state (`figmaVersion`, `figmaVersionLabel`, `figmaVersionCreatedAt`). `importName` is the key an agent uses to look the component up in Storybook; `keywords` are search aliases. Both are config, not extracted.
- **Images stay relative** with the section title as alt text, so the text remains meaningful for an agent that does not render images ([002](002-image-handling.md)).
- **`docs/index.md` is the generated entry point.** It explains the conventions, lists every document grouped by category with its code component, keywords, Figma version and a linked outline of H2/H3 chapters (GitHub style anchors, deduplicated like GitHub does). An agent reads this one file to decide what to fetch next. It is rebuilt from all documents on disk on every sync, so a partial `--component` run keeps it complete.
- Content is never rewritten, reordered or summarised. What designers write in Figma is what ends up in the file.

### Layer 2: curated AI guideline (out of scope here)

The 18 section template is the target shape for a document that combines design guidance with the component API. It is produced from layer 1 plus Storybook (props from `llms-full.txt` or the MCP server) by an agent or a person, and reviewed by UX. The mapping from Figma boards to template sections for the Accordion:

| Template section                     | Fed from layer 1                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------- |
| 1 Metadata                           | frontmatter (`importName`, `package`, `keywords`, `sourceUrl`, `figmaVersionCreatedAt`) |
| 2 Purpose, 3 Semantic Role           | overview board (first `##`), editorial                                                 |
| 4 When to Use, 5 When NOT to Use     | `Examples/Variants`, do and don't sections in `Content and Assets`                     |
| 6 Anatomy, 7 Variants                | `Formatting and Construction` (Anatomy, Size Variants, Chevron vs. Caret)              |
| 8 States                             | `Formatting and Construction` (Status, Motion), `Behavior`                             |
| 9 Content Rules                      | `Content and Assets` (Accessible copy, Accordion title, Custom hint area)              |
| 10 API / Properties                  | Storybook only                                                                         |
| 11 Composition                       | `Content and Assets` (Custom content area, Accordion group, nesting rules)             |
| 12 Responsive Behavior               | `Formatting and Construction` (Sizing, Minimum width)                                  |
| 13 Accessibility                     | `Behavior` (Focus management, The user is in control), `Content and Assets`            |
| 14 Correct Examples, 15 Anti-Patterns | do and don't sections, Storybook stories                                               |
| 16 Dependencies                      | `Related elements`, Storybook                                                          |
| 17 Implementation Notes, 18 Acceptance Criteria | editorial                                                                   |

Figma Specs ([DS-1537](https://andreasstihl.atlassian.net/browse/DS-1537)) could later make layer 2 an explicit Markdown document inside Figma, bootstrapped from layer 1.

## Alternatives considered

- **One file per section** (`docs/components/accordion/behavior.md`): finer granularity for fetching, but it multiplies files, breaks relative image paths across folders and duplicates frontmatter. Splitting by heading at serve time gives the same result from one file.
- **Renaming the overview board to `Overview`**: more meaningful than `Accordion single`, but it is a per-component alias that drifts from Figma. Rejected for layer 1; layer 2 is the place for editorial names.
- **Moving `Related elements` and `Further guidelines` into frontmatter**: structured data for agents, but detection is name based and the links lose their context. Kept in the body; the index already carries the code component.
- **A JSON sidecar with the block model**: lets a server render any shape, but doubles the diff on every sync. Not needed while the MCP server does not exist; `collectBlocks` can be called directly if it does.
- **Generating the 18 section template directly**: see Context. Rejected because the extractor would have to invent content.

## Consequences

- The MCP server (or the main repository importing these files) can treat `docs/index.md` as the catalogue and split documents by `##` without parsing Figma specific structure.
- Adding a component is one config entry (`id`, `title`, `category`, `importName`, `keywords`, `nodeId`, `output`, `imageDir`); the index updates itself.
- `importName` and `keywords` are maintained by hand in `components.config.json`. If the main repository later publishes a component manifest, they can be derived from it.
- Heading normalisation changes levels, not text, so Figma deep links and anchors stay stable when designers do start using H3 titles.
