# Findings: Figma documentation to Markdown (DS-1524)

## What works

- `npm run sync` turns the documentation pages of all four Figma team projects into `docs/<category>/<id>.md` with images next to it, and rebuilds [docs/index.md](docs/index.md): 14 foundations (Typography, Iconography, Grid & Spacing, Styles), 29 components (Core Components; List, Table and Segmented Control are skipped because their pages are "coming soon" or WIP), 4 patterns (Web Pattern Library) and 1 guideline (Onboarding). 48 documents, about 100 MB of PNGs at scale 1. The second run produces no diff (text, images, index).
- The output is shaped for agents, see [docs/decisions/003-markdown-structure.md](docs/decisions/003-markdown-structure.md): `docs/<category>/<id>.md` with the four categories mirroring the Figma team projects, stable `##` chapters taken from the designers' board template, no skipped heading levels so a file can be split by chapter, frontmatter with `importNames` / `package` / `keywords` to connect the design docs to the Storybook components, and a generated index as the entry point. Patrick Wiesenhuetter's 18 section AI guideline template ([docs/templates/ai-guidelines-template.md](docs/templates/ai-guidelines-template.md)) is the target for a curated second layer that combines this output with Storybook props; it is not something extraction can produce on its own.
- The documentation layout in Figma is regular enough for a rule based extraction: every board is `logo / title / divider / (sub-chapter | section)*`, every `section` is `Infos` (title, definition, optional link) plus `Frame For Specs`. Older pages (Button, Link) use a slightly different template (`_formatting`, `_overview`, `_content`, `_colour combinations`) and the foundation files use the same typography, so they extract without special cases. Only the Onboarding file has its own typography (80/48/40/32/24 px) and gets a per-source heading map. The mapping is config driven ([components.config.json](components.config.json)): one `sources` entry per Figma file, one `documents` entry per page.
- Headings, paragraphs, bold runs, hyperlinks (both node level and character level), ordered and unordered lists including nesting, images and callouts (`notification` instances, rendered as blockquotes) are extracted. Hidden layers (1846 on the Accordion page), template placeholders (`Link TO →`), loose text on the canvas or in sections, component definitions placed on the page (`COMPONENT`, `COMPONENT_SET`) and UI instances without a heading are dropped. The last two rules removed about a third of the Card page (card variants with their placeholder copy) and 120 `Label` paragraphs from a Combobox building block board, while documentation blocks built as components (`contribute`) are kept because they carry a heading.
- Change detection without any infrastructure: `npm run check` polls `GET /v1/files/:key/versions` of every source file for the newest **named** version and compares it with the frontmatter; `sync` reads nodes and images pinned to that version id (`?version=`). Designers publish by saving a named version, which they already do for component releases. See [docs/decisions/001-change-detection.md](docs/decisions/001-change-detection.md) for why the webhook relay was dropped.

## Access

- A personal access token with `file_content:read` and `file_metadata:read` is enough for extraction and image export. Reading and creating file-context webhooks worked as well, so no broader (team or org) access is required.
- Token ownership: for the spike the token belongs to a person. For production a token of a shared design system account (or an OAuth app) is needed so that the sync does not stop when someone leaves. Webhooks belong to the creating user too, same consideration.

## Limitations

- **Heading detection is heuristic.** The documentation text uses no Figma text styles (`styles.text` is empty on every documentation text node), so headings are detected by `fontSize` (64 = H2, 48 = H3, 24 = H4) **and** `fontWeight >= 600`; 24px regular text is a lead paragraph (Button page). Heading sized text longer than 120 characters or containing a "word" longer than 30 characters (lead sentences on the Onboarding page, font specimens on the Typography page) stays a bold paragraph. The size map is per config and can be overridden per source file. If designers change the template typography, the mapping must follow.
- **Reading order is geometric.** Children are sorted by `absoluteBoundingBox` (y, then x). This handles side-by-side boards and absolutely positioned text, but a text that visually belongs to a column could be interleaved with a neighbour if the y coordinates are within 8 px. Boards arranged in a grid are read row by row, which splits numbered board series on the Card page (`Layout 1/3`, `Sizing 1/3`, ..., `Layout 2/3`); chapters stay intact, only their order differs from the designers' column-wise intent.
- **Tables are not implemented.** None of the pages uses Figma `TABLE` nodes; tabular content (text style specs, token lists) is laid out with frames and ends up as a sequence of short bold paragraphs. Flag for the first page that uses real tables.
- **Unpublished files.** The Onboarding file has no named version, so it is synced from its current state (`allowUnpublished` on the source). Its documents show `unpublished state` in the index and `check` reports them outdated after every edit. Ask the owners to save a named version and remove the flag.
- **Line based paragraphs.** A line break inside a Figma text box becomes a new paragraph. Designers sometimes use spaces instead of line breaks for layout (`Animation type:  fade: ...  Duration: 100ms`), which then renders as one long paragraph.
- **Image framing is name based.** Only frames named `Frame For Specs` are exported. Decorative frames without text (icons, logos) are skipped, text containing frames are traversed. A frame that is meant as an illustration but has a different name would be flattened to its text.
- **Repository size.** At scale 2 the Core Components images alone were 150 MB (single boards up to 5500 px wide); scale 1 is the default now and all four projects add up to about 100 MB. Images of an unchanged Figma version are reused, so a sync only re-renders what changed. Git LFS or an external image host remain the fallback, see [docs/decisions/002-image-handling.md](docs/decisions/002-image-handling.md).
- **Hyperlinks to Figma nodes** (`type: NODE`) are turned into Figma deep links. Useful for designers, opaque for developers. A later step could map them to the generated Markdown of the target component.
- **Payload size and runtime.** The nodes response for a page is 7 to 12 MB because the spec frames contain every component variant. Figma renders images synchronously; a single Images request for a whole page (129 nodes on Card, 189 on Navigation) timed out, so exports go in batches of 20. A first full sync takes about 45 minutes, dominated by image rendering; later runs only render changed versions. The half-hourly `check` is one request per source file.
- **Rate limits.** The client retries on 429 (`Retry-After`), 5xx and network errors with exponential backoff.
- **Expiring image URLs** are handled by downloading immediately; nothing of the temporary URL ends up in the repository.

## Next steps towards the MCP server

1. **Remaining Figma files.** The team projects also contain the App Pattern Library (Beta), Helper, Playground and Archive files, and possibly further Fundamentals files (colors). The REST API cannot list a team's files without the team id, so these need their file keys added to `sources` by hand; each page is one `documents` entry. `importNames` and `keywords` stay manual until the main repository publishes a component manifest they can be derived from.
2. **Curated layer.** Compose the 18 section AI guideline per component from `docs/components/<id>.md` plus Storybook props (`llms-full.txt` or the MCP server), review by UX. The section mapping is in [docs/decisions/003-markdown-structure.md](docs/decisions/003-markdown-structure.md). Figma Specs ([DS-1537](https://andreasstihl.atlassian.net/browse/DS-1537)) is a candidate home for that layer.
3. **Tell designers about the publish rule.** Only named versions reach the documentation. The label is visible in the frontmatter and the pull request title, so a convention like `Docu | <component> | <ticket>` makes the history readable.
4. **MCP exposure.** The main repository already serves `https://designsystem.stihl.de/mcp` through `@storybook/addon-mcp` and generates `llms.txt`. Options: (a) the main repository pulls `docs/**/*.md` from this repository at build time and adds them as MCP resources next to the Storybook docs, or (b) a small standalone MCP server reads this repository directly. (a) keeps one endpoint for consumers and is the recommended direction. Either way `docs/index.md` is the catalogue and documents can be served per `##` chapter.
5. **Images for MCP.** Serve as resource URLs (raw GitHub or static host), never inline. See [docs/decisions/002-image-handling.md](docs/decisions/002-image-handling.md).
6. **Token and ownership.** Move the token to a shared account before the first scheduled run on GitHub; add `FIGMA_TOKEN` as a repository secret.
7. **Table support** when the first component with tables is added.
